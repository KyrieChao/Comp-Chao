# Comp-Chao

一个用 C 从零写的无损压缩工具：**LZ77 + 哈夫曼**。

不依赖任何第三方库，只用了标准库。压缩、解压、字节级无损。

选它的理由不是好用，是为了把压缩算法的每一步都亲手写一遍。

## 构建

```sh
gcc main.c huffman_algo.c lz77.c -O2 -Wall -Wextra -o comp-chao
```

换 Linux 机器跑不想缺 glibc 版本，加 `-static`：

```sh
gcc main.c huffman_algo.c lz77.c -O2 -static -o comp-chao
```

## 用法

```sh
comp-chao c <输入> [输出]      压缩；省略输出名时把扩展名换成 .chao
comp-chao d <压缩包> [输出]    解压；省略输出名时把扩展名换成 .txt，撞名自动加短 hash
```

```sh
comp-chao c demo.txt           # demo.txt -> demo.chao
comp-chao d demo.chao          # demo.chao -> demo.txt（已存在则 demo_5675.txt）
comp-chao c demo.txt out.chao  # 显式指定输出名，允许覆盖
```

## 实测

| 文件 | 原文 | 压缩后 | 比例 |
|---|---|---|---|
| `demo.txt`（C 源码 + 中文注释） | 8092 | **3641** | 45.0% |
| `demo.txt`（gzip -9 对照） | 8092 | 2828 | 34.9% |
| `test2.c` | 114 | 193 | 169.3% |

小文件会被头部开销吃掉（`test2.c` 就是），这是预期行为。

往返验证：所有样本（含 64KB 随机二进制）`fc /b` 逐字节一致，二进制安全。

## 工作原理

```
原文
 |  LZ77：在滑动窗口里找最长匹配
 |        找到 -> 输出 (距离, 长度)
 |        找不到 -> 输出字面量
 v
符号流(sym) + 距离流(dist)
 |  符号流走哈夫曼
 v
比特流 -> 打包成字节 -> 载荷
```

**两条流为什么要分开**：符号流里字面量和长度混在一起，分布偏斜，哈夫曼压得动；距离流的值散得多，是另一套分布，得单独处理。

### 文件格式

```
[data_len     : 4]              原文件字节数
[leaf_count   : 4]              哈夫曼叶子数 = 符号流里有几种不同符号
[struct_bytes : 4]              结构串压完占几个字节
[sym_n        : 4]              符号流有多少个符号
[dist_n       : 4]              距离流有多少个距离
[符号表       : leaf_count x 2] 每个叶子一个 unsigned short
[结构串       : struct_bytes]   前序遍历，内部节点 '1'、叶子 '0'，按位打包
[距离流       : dist_n x 2]     每个距离一个 unsigned short
[载荷         : 到文件尾]       符号流的哈夫曼码流，末字节补 0 对齐
```

**符号编码规则**（没有单独的 flag 字节）：

| 符号值 | 含义 |
|---|---|
| 0 ~ 255 | 字面量，值就是那个字节 |
| 257 ~ 512 | 匹配，长度 = 符号值 - 257 + 3（即 3 ~ 258） |

### 几个关键决定

- **为什么不用 flag 字节区分字面量和匹配**：字面量占文件的大头，加一个 flag 就让它从 1 字节变 2 字节，净亏。用**值域**区分则完全免费。
- **距离流为什么放在载荷前面**：这样载荷永远是文件的最后一段，长度可以直接用 `EOF - 当前位置` 算出来，不必再存一个长度字段。
- **符号表为什么按「叶子前序遍历顺序」而不是按值排序**：结构串和解码端往树上挂叶子的顺序必须严格一致，同一趟遍历产出两者，天然对齐。错位一个就全乱。
- **结构串为什么按位打包**：树的形状是一个 bit 一个标记，按字节存会浪费 8 倍（385 个 bit 本该占 49 字节，不是 385）。
- **`MAX_MATCH = 258`**：匹配长度必须封顶。长度符号的最大值是 `257 + 258 - 3 = 512`，字母表因此定为 513。不封顶的话长重复段会让符号值越界写坏内存。

## 代码结构

| 文件 | 职责 |
|---|---|
| `huffman_algo.c/h` | 纯哈夫曼：频次统计、建树、码表、结构串、从结构串重建树、编码、解码。**只认「符号」，不认「字节」** |
| `lz77.c/h` | 滑动窗口匹配，`lz77_encode` / `lz77_decode` 一对互逆函数 |
| `main.c` | 命令行、文件读写、比特打包、文件格式拼装。**字节世界和符号世界的边界在这里** |

分层的意义：`huffman_algo` 的接口收的是 `unsigned short*`（符号），它不知道字节是什么东西。字节到符号的转换（摊开）和符号到字节的转换（收拢）全都收在 `main.c` 一层。换压缩算法时，被替换的是 `lz77.c`，哈夫曼那一层一行都不用动。

## 待办
