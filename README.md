# Comp-Chao

一个用 C 从零写的无损压缩工具：**LZ77 + 哈夫曼**。

不依赖任何第三方库，只用了标准库。压缩、解压、字节级无损。

选它的理由不是好用，是为了把压缩算法的每一步都亲手写一遍。

> **当前状态**：距离档位编码（Deflate 那套「档位符号 + 额外位」）已完整落地，压缩解压都跑通，全部样本 `fc /b` 逐字节一致。

## 构建

```sh
gcc main.c huffman_algo.c lz77.c -O2 -Wall -Wextra -o comp-chao
```

换 Linux 机器跑不想缺 glibc 版本，加 `-static`：

```sh
gcc main.c huffman_algo.c lz77.c -O2 -static -o comp-chao
```

## 用法

```sh
comp-chao c <输入> [输出]      压缩；省略输出名时把扩展名换成 .chao
comp-chao d <压缩包> [输出]    解压；省略输出名时把扩展名换成 .txt，撞名自动加短 hash
```

```sh
comp-chao c demo.txt           # demo.txt -> demo.chao
comp-chao d demo.chao          # demo.chao -> demo.txt（已存在则 demo_5675.txt）
comp-chao c demo.txt out.chao  # 显式指定输出名，允许覆盖
```

## 实测

| 文件 | 原文 | 压缩后 | 比例 |
|---|---|---|---|
| `demo.txt`（C 源码 + 中文注释） | 8092 | **3242** | 40.1% |
| `demo.txt`（gzip -9 对照） | 8092 | 2828 | 34.9% |
| 64KB 文本语料 | 65536 | **13884** | 21.2% |
| 64KB 随机字节 | 65536 | 66220 | 101.0% |

小文件会被头部开销吃掉，压不动甚至变大（随机数据就是），这是预期行为。

往返验证：每次文件格式改动都会跑 `fc /b` 逐字节比对。距离档位编码落地后，三个样本（`demo.txt` / 64KB 语料 / 64KB 随机）全部逐字节一致。

## 工作原理

```
原文
 |  LZ77：在滑动窗口里找最长匹配
 |        找到 -> 输出 (距离, 长度)
 |        找不到 -> 输出字面量
 v
符号流(sym) + 距离流(dist)
 |            |
 |            +-> 距离映射成「档位号 + extra 位」，档位号再哈夫曼编码
 +-> 哈夫曼编码
 v
两条码流分别按位打包 -> 拼成 .chao
```

**两条流为什么要分开**：符号流里字面量和长度混在一起，分布偏斜，哈夫曼压得动；距离流的值散得多，是另一套分布，得单独处理。

### 文件格式

```
[data_len       : 4]               原文件字节数
[leaf_count     : 4]               符号树叶子数 = 符号流里有几种不同符号
[struct_bytes   : 4]               符号树结构串压完占几个字节
[dist_bytes     : 4]               距离段压完占几个字节
[sym_n          : 4]               符号流有多少个符号
[dist_n         : 4]               距离流有多少个距离
[d_leaf_count   : 4]               档位树叶子数 = 距离流用到几种档位
[d_struct_bytes : 4]               档位树结构串压完占几个字节
[符号树结构串   : struct_bytes]    前序遍历，内部节点 '1'、叶子 '0'，按位打包
[符号表         : leaf_count x 2]  每个叶子一个 unsigned short，按叶子前序遍历顺序
[档位树结构串   : d_struct_bytes]  编码方式同上
[档位表         : d_leaf_count x 2] 每个叶子一个 unsigned short
[距离段         : dist_bytes]      每条「档位哈夫曼码 + extra 位」，按位打包
[载荷           : 到文件尾]        符号流的哈夫曼码流，末字节补 0 对齐
```

**距离编码规则**：档位表用的是 Deflate 标准那套，共 30 档。`d_base[30]` 是每档的起始距离，`d_extra[30]` 是每档还要再写几位额外位，两张表在 `main.c` 顶部。近档位 extra 短（档位 0~3 是 0 位），越远越长（档位 29 是 13 位）；所以「距离段」里每条 = 档位号的哈夫曼码 + extra 位。

**符号编码规则**（没有单独的 flag 字节）：

| 符号值 | 含义 |
|---|---|
| 0 ~ 255 | 字面量，值就是那个字节 |
| 257 ~ 512 | 匹配，长度 = 符号值 - 257 + 3（即 3 ~ 258） |

### 几个关键决定

- **为什么不用 flag 字节区分字面量和匹配**：字面量占文件的大头，加一个 flag 就让它从 1 字节变 2 字节，净亏。用**值域**区分则完全免费。
- **距离流为什么放在载荷前面**：这样载荷永远是文件的最后一段，长度可以直接用 `EOF - 当前位置` 算出来，不必再存一个长度字段。
- **距离为什么不再定长**：一开始每个距离固定 2 字节，后来改成 `dist_bits` 位定长（`demo.txt` 里最大距离才 7197，13 位就够，定死 16 位等于白扔 3 位）。但这仍然是「所有距离一样贵」，而近的距离（1、2、3……）明明远多于远的。现在换成 Deflate 那套：距离先映射到 30 个档位之一，档位号再配若干额外位。档位号的分布本身也是偏斜的，所以 `A2b` 干脆给档位号单独建了一棵小的哈夫曼树——`demo.txt` 上距离段从 1241 降到 1160 字节。代价是多存一棵档位树的表（这里约 57 字节），距离条数越多越划算。
- **符号表为什么按「叶子前序遍历顺序」而不是按值排序**：结构串和解码端往树上挂叶子的顺序必须严格一致，同一趟遍历产出两者，天然对齐。错位一个就全乱。
- **结构串为什么按位打包**：树的形状是一个 bit 一个标记，按字节存会浪费 8 倍（385 个 bit 本该占 49 字节，不是 385）。
- **`MAX_MATCH = 258`**：匹配长度必须封顶。长度符号的最大值是 `257 + 258 - 3 = 512`，字母表因此定为 513。不封顶的话长重复段会让符号值越界写坏内存。

## 代码结构

| 文件 | 职责 |
|---|---|
| `huffman_algo.c/h` | 纯哈夫曼：频次统计、建树、码表、结构串、从结构串重建树、编码、解码。**只认「符号」，不认「字节」** |
| `lz77.c/h` | 滑动窗口匹配，`lz77_encode` / `lz77_decode` 一对互逆函数 |
| `main.c` | 命令行、文件读写、比特打包、文件格式拼装。**字节世界和符号世界的边界在这里** |

分层的意义：`huffman_algo` 的接口收的是 `unsigned short*`（符号），它不知道字节是什么东西。字节到符号的转换（摊开）和符号到字节的转换（收拢）全都收在 `main.c` 一层。换压缩算法时，被替换的是 `lz77.c`，哈夫曼那一层一行都不用动。
